## 一、关键架构设计（5 个设计决策 + 为什么）

> 讲「设计」的重点是**为什么这么设计**，不是罗列模块。每条标它命中的评分维度。

### ① 六节点直线流水线 + 单一 AgentState

- **设计**：`意图识别 → 采集 → 分析 → 撰写 → 质检 → 终审` 编排成**无环直线 DAG**（LangGraph StateGraph）；Agent 之间不做自然语言对话，传一份字段冻结的共享工单 `AgentState`，各自往里填自己那栏。
- **为什么**：
  - 结构化消息传递（非闲聊）→ 命中 35%「标准 Schema 传递」
  - 中间产物全程留痕 → 可观测、可回放
  - 无环 → 工程上杜绝死循环
- **挣分句**：「Agent 间传的是结构化工单，不是自然语言，每个节点的输入输出都能审计。」

### ② 三个「唯一 owner」+ AST 测试锁边界（最体现架构功力）

- **设计**：把三件最易越界的事各焊死给一个 owner——
  - 缺口判定 → `evidence_gaps`（唯一入口 `find_gaps`）
  - 采集执行 → `evidence_service`（唯一入口 `fill`）
  - 结论强度 → `guard`（唯一入口 `apply`）

  并写 **AST 静态测试**自动校验 Analyzer 里没有任何采集 import，越界即测试红。
- **为什么**：用**代码层面的硬约束**保证「职责边界明确、无重叠」，比口头说「我们分工清晰」强得多。
- **挣分句**：「边界不是靠自觉，是靠 AST 测试守的——分析层一旦碰采集就挂测试。」→ 直接命中 35% 评分原句。

### ③ 「契约 + 可观测」开发方法论（项目灵魂）

- **设计**：每个阶段先定义「输入 → 输出契约」（该产出什么），再用 `logs/stage_quality.jsonl` 逐阶段记可量化指标（覆盖率/相关性/质量分/幻觉数/缺口数/耗时）去验证实际产出，发现「实际 ≠ 预期」就修。
- **为什么**：这是「质量优化靠可观测」的方法论落地——所有的坑都是看这些指标看出来的。
- **挣分句**：「我做的核心不是调大模型，是给每个阶段装上可观测的仪表盘。」→ 命中 25%「可观测性达标」。

### ④ 闭环下沉：直线 + 阶段内自检 + 确定性终门（核心架构演进）

- **设计**：从早期「带环打回状态机」演进为三层——
  - **阶段内自愈**：采集/分析出口就自检，缺了定向补采
  - **独立 Reviewer 只审不修**：跑 R0–R10，输出问题清单 + 归因标签
  - **guard 确定性终门**：基于证据一次性清理降级，幂等、无环、修不掉就诚实降级
- **为什么**：实测 54 run 跨节点打回仅触发 1 次 → 用数据驱动把复杂状态机删掉，换直线。
- **挣分句**：「质检闭环是真的、会触发、且一定收敛——但我用实测数据把它从带环状态机简化成了直线。」→ 命中 35%「反馈闭环非伪」+ 25%「前瞻性」。

### ⑤ 三层降级 + 泛化双路径

- **设计**：
  - 采集三层降级 `live → cache → mock`；搜索多供应商 `Brave → Tavily → DDG`
  - 泛化走「LLM 动态发现竞品（主路径）+ YAML 兜底（断网/无 key/Demo 种子）」
- **为什么**：稳定性（断网也能跑）+ 真泛化（换行业零改码，只换 LLM 发现的对手）。
- **挣分句**：「换个行业，不用改一行代码——竞品是 LLM 现场发现的，YAML 只兜底。」→ 命中 25%「降级机制」+ 20%「可换行业」。

## 二、技术难点（6 个，难点 → 方案 → 效果）

> 讲「难点」按「问题有多难 → 我怎么解 → 效果/证据」展开。

### 难点 1 · LLM 长输出截断 + 倒推幻觉

- **难在哪**：一次生成整篇报告 → JSON 截断、残缺无法解析；模型「先想结论再倒编证据」。
- **方案**：拆 **facts → derivations 两步** + facts 内部三 section 并行 + 证据压缩分桶 top-K + 每步 `quick_validate` 自评估 + 尾部 JSON 修复兜底。
- **效果**：单次输出体量减半，截断率显著下降；结论必挂已抽事实，证据不足输出 `unknown`。

### 难点 2 · 结论级溯源（每句可点回原文）

- **难在哪**：段落级引用太粗，LLM 会编造来源 ID。
- **方案**：`evidence_id` 对证据内容做**确定性 hash**（`"S"+sha1(...)[:7]`，**编都编不出来**）+ 每条 claim 句末打 `[SXXXXXXX]` chip + Reviewer R1/R9 校验引用真实存在。
- **效果**：每条结论可一键跳原文 / URL / 可信度；伪造引用被自动拦截。

### 难点 3 · 质检既要可信、又要可终止

- **难在哪**：规则太严会死循环，太松又失信。
- **方案**：三层质检下沉（节点内自愈 + 独立 Reviewer 只审不修 + guard 确定性终门），直线无环；实测 **54 run 仅 1 次触发跨节点打回** → 删掉复杂打回状态机。
- **效果**：闭环真实可触发且必收敛，无死循环。

### 难点 4 · 全量打回低效（「20 分钟」故事）

- **难在哪**：只缺一格却**全量重抓**，检索不到反复重试同一批词 → 一次跑了 **20 分钟还没结束**。
- **方案**：**闭环前置**到采集阶段内部 + **定向补采**（只补缺的 product × claim_type）+ 检索不到走**策略阶梯**换方法（站内 → 全网 → 中英别名 → 官网 SPA 渲染 → 诚实标「不可得」）+ 轮次上限。
- **效果**：**从 20 分钟跑不完，到一次约 4 分钟、约 5 倍提速，且可终止。**

### 难点 5 · 采集质量（无关信息 + 定价缺漏）

- **难在哪**：搜到就用会混入无关帖（理财帖混进 AI 工具分析）；定价表是 JS 渲染抓不到。
- **方案**：`quality.py` 5 维质量分 + **相关性硬门**（≥70% 真提产品名）+ 营销空话 fluff 检测；定价走 **Playwright SPA 渲染** + 出处锚定。
- **效果**：相关性差的宁可少收；定价能抓到真实档位价（本地环境）。

### 难点 6 · 并发提速但防串台

- **难在哪**：并发是提速关键，但最容易让多个运行的进度/Token 混在一起串台。
- **方案**：`ContextVar` + 自定义 `CtxThreadPoolExecutor` 跨线程隔离上下文；采集四适配器并发 + 分析三 section 并行。
- **效果**：并发提速的同时运行互不串台——这个 bug 正是靠可观测日志发现并修掉的。
