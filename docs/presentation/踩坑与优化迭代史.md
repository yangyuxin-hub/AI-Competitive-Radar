## 开场论点(整个项目的灵魂)

> **Demo 我很快就做好了——能跑通、能出一份报告，不难。真正难的是把最终报告的质量做上去。**
> **而质量优化的前提，是我对每个环节都完全可观测、可控**：我得能看见每个阶段实际产出了什么，才能发现它跟我的预期差在哪、然后去修。
> 所以我做的是一套方法：**给每个阶段定义清楚输入/输出契约 → 用可观测性检查实际产出 → 发现『实际 ≠ 预期』的缺漏（踩坑）→ 修正对齐。**
> 下面按**用户真实使用的阶段顺序**，讲我在每个阶段观测到了什么问题、做了什么改进。

**贯穿全程的主角是「可观测性」**：`logs/stage_quality.jsonl` 给每个阶段记录可量化指标（覆盖率/相关性/质量分/幻觉数/缺口数/耗时），`logs/llm_calls.jsonl` 记录每次 LLM 调用全量。**我所有的坑，都是在看这些指标时发现的。**

## 阶段一 · 意图识别

**我期望它输出**：从用户一句话里解析出 target、竞品列表、分析焦点、分析意图，并生成"该采哪几类证据"的契约。

| 观测到的问题 | 改进 | 证据 |
|---|---|---|
| 行业泛化不能靠人工写死 YAML（会过时、换行业抓瞎） | **LLM 动态发现竞品**：有 key 时 `call_json` 智能推荐最新同类竞品（含陌生竞品）；YAML 仅作无 key/Demo 兜底种子 | `intake.py` 设计要点 |
| 竞品名中英文/变体不统一（可灵 vs Kling），召回对不上 | 竞品候选**跨语言/变体去重** + 别名归一 | commit `3573cb4` |
| "为什么用户流失"这类**痛点问题**被框成逐功能 0-5 跑分，逼分析硬凑推测 | 加意图识别 `_detect_intent`：痛点归因类走"痛点焦点"而非功能跑分 | `intake.py:75` |

> 这一阶段的可控点：用户不硬填字段，而是 agent 给候选 + 推荐、用户做选择题——人决策点都收敛成可观测的选项。

## 阶段二 · 信息采集

**我期望它输出**：raw_evidence 列表，四类核心证据（功能/性能/定价/痛点）每个产品都覆盖，每条带来源、质量分、相关性。

| 观测到的问题 | 改进 | 证据 |
|---|---|---|
| 采集"搜到就用"，**混入大量无关信息**（理财帖混进 AI 工具分析） | `quality.py` 5 维质量分 + **相关性硬门**（≥70% 真提产品名）+ 营销空话 fluff 检测，入库前把关 | — |
| **定价缺漏**：定价表是 JS 渲染的，普通抓取拿不到 | 定价验收门（检测"联系销售"无数字）+ **L3 官网 SPA 渲染**（Playwright）+ 定价证据出处锚定 | commit `88fd53d` |
| live 抓取不稳、怕断网 | **三层降级 live→cache→mock** + 搜索 Brave→Tavily→DDG 多供应商降级 | — |
| 采集失败只会重试同一批词 | **ReAct 自愈补采**：验收门审计→诊断缺口类型+生成处方→定向补采（不是 retry） | — |

> 这一阶段的可观测：stage 日志记 coverage_ratio / avg_quality / relevance_ratio / gaps_open——**我就是看这几个指标，发现"相关性只有 5 成""定价桶没有真实价格"这些坑的。**

## 阶段三 · 信息处理(分析)

**我期望它输出**：结构化 schema（功能树/定价/画像/SWOT/建议），每个结论挂真实 evidence_ids，证据不足输出 unknown，不编造。

| 观测到的问题 | 改进 | 证据 |
|---|---|---|
| 一次性生成整篇 → **JSON 截断**、残缺无法解析 | 拆 **facts→derivations 两步** + facts 内部三 section 并行，单次输出体量减半 | — |
| 证据太多 payload 爆炸 → 超时 | 证据压缩 `_compact_evidence`：按(类型×产品)分桶 top-K + 近似去重 + 截短 | — |
| 截断后整轮失败 | LLM 尾部 JSON **修复兜底** | commit `217b3c2` |
| **倒推式幻觉**：先想结论再倒编证据；编造 evidence_id | 两步式（结论必挂事实）+ evidence_id 确定性 hash（编不出）+ 不足输出 unknown | — |
| 引用难追溯、信息混乱 | Writer 每条 claim 打 `[SXXXXXXX]` chip + 字段冻结 Schema 强制结构 | — |
| 问题都等下游才发现 | Analyzer 每步 `quick_validate` 自评估 → 立即确定性 sanitize 自愈 | — |

> 这一阶段的可观测：stage 日志记 hallucination_count（应 0）/ unknown_ratio / chip_traceable_ratio——**幻觉数不为 0、chip 对不上，我立刻能看到。**

## 阶段四 · 报告产出与质检

**我期望它输出**：结构完整、每条结论可溯源、不达标会被拦下或诚实降级的最终报告。

| 观测到的问题 | 改进 | 证据 |
|---|---|---|
| 质检规则太严会死循环、太松又失信 | 三层质检下沉：节点内自愈 + 独立 Reviewer 只审不修 + guard_revise 确定性终门，直线无环 | M1-M4 见下 |
| 早期打回闭环过度设计（实测 54 run 仅 1 次触发） | 删打回回流 + retry 配额 + degraded_writer，改一次确定性修订 | commit `716a50f` `23ede55` |
| 报告该诚实标注不可得，不能编 | 修不掉的缺口走 degraded 分层降级，诚实标"定价不可得"而非编价 | `guard._degraded_annex` |

**质检演进里程碑**：M1 统一缺口判定+池内回捞 `203aaf4` → M2 Guard 收编结论强度 `a6586aa` → M3 拆 EvidenceService `2c5e514` → M4 直线控制流 `716a50f`。

## 横切优化 · 时间效率(后期专门做的提速)

> 质量做扎实后，针对"跑太慢"专门做了一轮提速——这一节单独讲，体现工程完整度。

| 优化方向 | 做了什么 | 效果 |
|---|---|---|
| **并发执行** | 采集器 AdapterRegistry 并发跑四适配器；分析 facts 三 section（feature/pricing/persona）用线程池**并行** | 串行变并行，墙钟时间显著下降 |
| **拆解提示词** | 把"一次大 prompt"拆成 facts→derivations 两步 + 三 section 各只喂相关证据、只输出自己那段 | 输出量减半/三分，躲开 max_tokens 截断悬崖，还更快 |
| **payload 瘦身** | prompt_slim：砍 LLM 用不到的 meta 字段；derivations 用更紧的 top-K/片段长 | prompt 体积降 23~38%，推导 74s→40s，盲评零掉分 |
| **thinking 优化** | 隐藏思维链占 43-91% completion token；机械分类默认关 thinking，深度推理才开 | 机械分类 24.8s→1.4s | commit `288c84a` |
| **并发隔离** | ContextVar + CtxThreadPoolExecutor，并发提速的同时防止跨 run 进度/token 串台 | commit `a247ff0` |

> 关键：**并发和拆 prompt 是"提速"，但前提是可观测**——因为并发最容易引入"串台"bug（多个 run 的进度/token 混在一起），我正是靠日志发现并修掉了串台（`a247ff0`），才敢放心并发。

## 一句话串起来(答辩可直接用)

> Demo 容易，质量难。我把流水线拆成意图识别→采集→处理→质检四个阶段，给每个阶段定义清楚"该输出什么"，再用可观测性逐阶段检查"实际输出了什么"——所有的坑都是这么观测出来的：意图阶段竞品中英对不上、采集阶段混入无关信息和定价缺漏、处理阶段截断和幻觉、质检阶段死循环。一个个修完，最后再用并发和拆提示词把速度提上来。**整个过程的主角不是大模型，是可观测性。**
