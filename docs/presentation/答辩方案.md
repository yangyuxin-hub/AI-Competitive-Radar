## 1 · 开场与背景（2′）

**讲什么**：
- 一句话定位：「输入一句话『分析 X 和 Y 在 Z 维度的差距』→ 自动产出结构化竞品报告，每条结论可一键溯源到原始证据。」
- 传统人工竞品分析的痛点：慢（约 8 工时）、信息源窄、格式因人而异、**结论难溯源**（"这条结论你从哪看来的？"答不上来）。
- Demo 场景：AI 编程工具 Cursor / Windsurf / GitHub Copilot，分析焦点「代码补全体验」。

**一句话钩子**：「我做的不是『让大模型写一篇竞品报告』，而是把竞品分析拆成一条**可审计、可溯源、可降级**的 Agent 流水线。」

## 2 · 整体方案：多 Agent 架构（4′）

**讲什么**（配架构图）：
- 六节点专职流水线，LangGraph 编排成**直线有向图**：
  ```
  evidence_planner → collector → analyzer → writer → reviewer → guard_revise → END
   规划员            采集员       分析员      撰写员    质检员      终审修订员
  ```
- 每个 Agent **只干一件事**，职责边界用「三个唯一 owner」焊死：
  - 缺口判定 → `evidence_gaps`
  - 采集执行 → `evidence_service`
  - 结论强度 → `guard`
  - **并用 AST 测试自动校验** Analyzer 里没有任何采集 import，从代码层面保证边界无重叠。
- Agent 之间不"聊天"，而是传一份共享工单 `AgentState`（结构化字典），每个 Agent 往里填自己那一栏 → **结构化消息传递，非自然语言对话**。

**点睛**：「LangGraph 把『节点 + 边 + 共享状态』显式建模，所以这条流水线每一步都可观测、可追溯、可回放。」

## 3 · 核心技术：关键架构设计 + 技术难点（8′）

> 这一节正面回应答辩要求「展示关键架构设计与技术难点」。
> **完整稿见 `关键架构与技术难点.md`（可直接转 PPT）；现场口头按 `汇报脚本.md` 的"按阶段讲优化故事"走。** 下面是浓缩版。

### 3.1 关键架构设计（先讲 3′ 设计决策 + 为什么）

1. **六节点直线 DAG + 单一 AgentState**：无环流水线，Agent 间传字段冻结的结构化工单（非自然语言对话）→ 命中 35% 结构化协作 + 全程可观测可回放。
2. **三个唯一 owner + AST 锁边界**：缺口判定 `evidence_gaps` / 采集执行 `evidence_service` / 结论强度 `guard` 各一个 owner，AST 测试自动校验分析层不碰采集 → **边界无重叠靠代码守，不靠自觉**。
3. **「契约 + 可观测」方法论**：每阶段先定输入/输出契约，再用 `stage_quality.jsonl` 逐阶段验证实际产出——所有坑都是看指标看出来的（项目灵魂）。
4. **闭环下沉：直线 + 阶段内自检 + 确定性终门**：实测 54 run 打回仅 1 次 → 删带环打回状态机，换"自愈 + Reviewer 只审不修 + guard 终门"。
5. **三层降级 + 泛化双路径**：采集 live→cache→mock、搜索 Brave→Tavily→DDG；竞品走 LLM 动态发现（主）+ YAML 兜底 → 断网能跑、换行业零改码。

### 3.2 技术难点（再讲 5′，难点→方案→效果）

1. **长输出截断 + 倒推幻觉** → 两步式 facts→derivations + 三 section 并行 + 证据压缩 + quick_validate 自评估 → 截断率降、结论必挂事实、不足输出 unknown。
2. **结论级溯源** → evidence_id 确定性 hash（编不出）+ `[SXXXXXXX]` chip + R1/R9 校验 → 每句可点回原文，伪造引用被拦截。
3. **质检既可信又可终止** → 三层下沉 + 直线（54:1 实测驱动）→ 闭环真实可触发且必收敛、无死循环。
4. **全量打回低效（20 分钟故事）** → 闭环前置 + 定向补采（只补缺的那一格）+ 策略阶梯换检索方法 + 轮次上限 → 20min → 约 4min、约 5× 提速且可终止。
5. **采集质量（无关信息 + 定价缺漏）** → 5 维质量分 + 相关性硬门（≥70% 真提产品）+ Playwright SPA 渲染 → 少收无关、抓到真实档位价。
6. **并发提速但防串台** → ContextVar + CtxThreadPoolExecutor 隔离上下文 → 提速且跨 run 不串台（靠日志发现并修掉）。

## 三、功能说明

**核心功能清单**：
1. **多 Agent 协作分析**：六节点专职流水线，覆盖「规划证据 → 采集 → 分析 → 成文 → 质检 → 终审修订」全链路。
2. **结构化竞品知识抽取**：功能树 / 定价模型 / 用户画像 / SWOT / 优先级建议，统一冻结 Schema，跨报告格式一致、字段可校验。
3. **结论级证据溯源**：所有关键结论引用确定性 `evidence_id`，正文以 `[SXXXXXXX]` chip 标注，可点击查看原始片段 / URL / 来源偏向 / 可信度。
4. **三层质检 + 确定性终门**：节点内自评估自愈 + 独立 Reviewer 出定位清单 + `guard_revise` 一次确定性修订，反馈闭环真实可触发。
5. **三层采集降级**：live → cache → mock，网络不稳或无 key 时仍完成端到端演示。
6. **全链路可观测**：StageReport 统一契约 + Timeline / Checklist 视图，每步产物数 / 缺口 / 耗时 / 修订均可追溯。
7. **问卷设计与合成用户访谈**：真实 UGC 不足时自动设计 4-6 道针对性问卷、LLM 扮演多样画像作答，透明标注为合成数据，绝不冒充真实反馈。

**端到端使用流程**：
1. 用户输入自然语言需求 → 2. Intake 解析意图、不足则澄清 → 3. Evidence Planner 生成声明式采集契约 → 4. Collector 三层采集 → 5. Analyzer 两步式分析 → 6. Writer 渲染 + 打 chip → 7. Reviewer 质检 + guard_revise 修订 → 8. 用户在报告页查看结构化结果、质量徽章、证据抽屉。

## 四、技术说明

### 4.1 系统架构

```
用户输入 → Next.js 前端 →(HTTP/SSE)→ FastAPI 后端 → LangGraph 编排
  evidence_planner → collector → analyzer → writer → reviewer → guard_revise → 报告输出
                        ↓             ↓
                  公开网页/搜索      LLM(豆包/MiMo)
                  Brave→Tavily→DDG
```

### 4.2 六个 Agent 的职责与边界

| Agent | 职责 | 禁止 |
|---|---|---|
| evidence_planner | 把意图转成声明式采集契约（必需 / 可选 claim type） | 不采集 |
| collector | 三层降级抓 raw_evidence + 验收门自愈补采 | 不做分析、不下结论 |
| analyzer | 两步式填充 schema（feature/pricing/persona/swot/rec）+ 自评估 | 不抓数据、不编 evidence_id |
| writer | 渲染 Markdown + 打 chip | 不改 schema |
| reviewer | 跑 R0-R10 规则、出结构化定位清单 | 只审不修 |
| guard_revise | 消费定位清单做一次确定性修订定终态 | 只降级 / 删除，不新增内容 |

### 4.3 关键技术点（对齐评分项）

**① 结构化消息传递**：Agent 间传 `AgentState`（TypedDict 字典），字段冻结，非自然语言对话。

**② 上下文管理 / 超长上下文分片**：
- 证据压缩 `_compact_evidence`：按 (claim_type × 产品) 分桶取 top-K + 近似去重 + 片段截短，几十条证据压到 ~8K token。
- 任务分片：两步式 facts→derivations + facts 内部三 section 并行（每片只喂相关证据、只输出自己那段），躲开 max_tokens 截断悬崖。
- payload 瘦身（prompt_slim）+ 截断 JSON 修复兜底。
- **压缩不损溯源**：喂 LLM 用压缩版，evidence_id 校验用全量。
- 运行时上下文隔离：ContextVar + CtxThreadPoolExecutor 防并发 run 串台。

**③ 幻觉抑制**：两步式 + 只基于 extracted_snippet + 证据不足输出 unknown + 禁编 evidence_id + quick_validate 自评估 + R1/R9 引用强制校验。

**④ 错误恢复 / 降级**：三层采集降级 + 多搜索供应商降级 + 节点内自愈补采 + guard 降级分层输出。

**⑤ 反馈闭环**：三层质检下沉（见第一部分 3(b)），直线控制流根除死循环。

### 4.4 关键工程难点（问题 → 方案 → 效果）

> 完整 6 条见 `关键架构与技术难点.md` 第二部分。核心三条：

- **难点 · LLM 长输出截断 + 事实/推导互相污染** → Analyzer 拆 facts→derivations 两步 + 三 section 并行 + 证据压缩 + quick_validate 自评估 → 截断率显著下降，源头压制倒推式幻觉。

# 第三部分 · 20 分钟问答预案

> 按"高危 → 常规"排序。高危题先背熟。

### 高危：反馈闭环真伪（直接关系 35%）
- **Q：你们质检能打回采集 / 分析重做吗？**
  A：能，但我们做了更优的设计。我最初实现过完整的"打回上游重做"闭环，但实测 54 次运行跨节点打回只触发 1 次——绝大多数问题在节点内就能自愈。于是把闭环**下沉为三层**：节点内自评估自愈 + 独立 Reviewer 定位 + guard_revise 确定性终门修订。现场我可以演示一处被质检抓到、被确定性修订掉的内容（前后对比），证明这是真闭环不是伪闭环。
- **Q：那"重做后输出有改善"怎么体现？**
  A：看质检前后对比——修订前报告有一条幻觉引用 / 过度泛化，Reviewer 标出来，guard_revise 把它清理 / 收敛，报告重渲染。前后两版可并排展示，改善可见。

### 幻觉抑制
- **Q：怎么保证不编 evidence_id？**
  A：三重——① evidence_id 是对证据内容做确定性 hash，编不出来；② Prompt 强约束事实只能基于 extracted_snippet、不足输出 unknown；③ R1/R9 校验每个引用真实存在，断链即标记。

### 上下文管理
- **Q：证据几十条怎么塞进上下文？删了会不会丢信息？**
  A：分桶取 top-K + 近似去重压到 ~8K token；按产品分桶保底不挤空某产品（实测修过 Linear 定价被全局截断的 bug）；任务按语义分片（两步 + 三 section）；全量证据仍用于溯源校验。

### 可观测
- **Q：单个 Agent 的 Prompt / 决策 / Token 怎么看？**
  A：`logs/llm_calls.jsonl` 全量记录每次调用的 system prompt / 输入 / 输出 / token，按 run_id + stage 归因；`logs/stage_quality.jsonl` 记录每节点的产物数 / 缺口 / 耗时；前端 Timeline / Checklist 实时可视。现场可翻日志。

### 业务落地
- **Q：换行业要改代码吗？**
  A：不用。产品 / 行业 / 评分 / Prompt 全部配置化（products / domains / scoring.yaml + prompts/），已内置 9 个行业域，现场演示切换。

### 合规
- **Q：数据采集授权？访谈数据怎么处理？**
  A：只采公开信息、遵守 robots.txt、标注来源偏向；合成访谈透明标注 synthetic、不冒充真人；访谈 / 问卷脱敏。

### 互动 / 后续方向
- **Q：后续怎么优化？**
  A：RAG 向量召回提升证据相关性、扩展更多行业域、公网稳定部署、把 54:1 这类实测沉淀成持续的质量看板。
