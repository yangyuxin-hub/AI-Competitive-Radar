# 企业内部竞品分析 · 使用场景叙事

> 用途：回答「企业 PM / 数据分析师在真实工作里，什么时候会触发竞品分析、想要什么、判断标准是什么」。
> 这是产品视角的需求叙事文档，不是技术设计。它是 `design-v2.2.md` 的上游——架构、Agent 角色、Schema、触发模式都应当从这里的场景反推。
> 配套：分析方法论见 `competitive-analysis-playbook.md`，赛题边界见 `task-requirements.md`。

---

## 0. 为什么先写场景

竞品分析系统最容易跑偏的方式，是把自己做成「一个更好的搜索摘要器」。要避免这一点，必须先承认一个事实：

**「竞品分析」不是一种需求，而是一类需求的统称。** 同样一句「帮我分析竞品」，背后的真实诉求、触发时机、可接受的输出形态、信源要求都完全不同。一个 PM 在新赛道立项时要的是「全景地图」，在竞品突发大更新时要的是「半天内能交的一页 brief」——这两者用同一个模板硬套，结果一定是两边都不满意。

所以本文档按「触发时机」拆 6 个真实场景。每个场景回答四件事：

1. **谁、在什么压力下、说了什么**（触发语境）
2. **输入是什么**（系统拿到的起点）
3. **想要什么输出**（PM 心里的成品）
4. **这个场景悄悄要求系统具备什么能力**（隐含需求，反推设计的关键）

---

## 场景 1：新赛道立项 / 0→1 探索

> 「老板说想看看要不要做 AI 搜索独立 App，下周一过会，给我一份全景。」

| 维度 | 内容 |
|------|------|
| **触发语境** | 高层抛出一个方向性想法，PM 需要在过会前快速建立「这个赛道值不值得进」的判断。时间紧、信息从零开始。 |
| **输入** | 一个赛道关键词（如「AI 搜索」），可能连竞品名单都没有。 |
| **想要的输出** | 玩家地图（谁在做、分几层）、市场空白点、差异化机会、主流商业模式对比。 |
| **PM 的成功标准** | 过会时能说清「赛道里有哪几类玩家、空白在哪、如果做我们切哪个口」。要的是判断依据，不是产品罗列。 |

**隐含的系统能力**

- **广撒网式采集** > 精准比对：连竞品名单都要系统帮忙发现，不能假设输入里已有 competitors。
- **归纳能力** > 逐项打分：核心价值是「把散点聚成玩家分层和空白地图」，而非功能矩阵。
- 输出偏「地图 / 分层」，不是「A vs B 对比表」。

---

## 场景 2：功能 Roadmap 规划

> 「下季度 OKR 要不要把 AI 会议纪要列进来？三家友商都做了啥、用户怎么评价、做的话差距多大？」

| 维度 | 内容 |
|------|------|
| **触发语境** | 季度 Roadmap / OKR 评审前，PM 要为「要不要做某功能」找弹药，需要量化差距和投入产出。 |
| **输入** | 一个候选功能名 + 通常已有明确的竞品名单。 |
| **想要的输出** | 各家功能成熟度矩阵、用户反馈摘要、技术实现路径、ROI 估算。 |
| **PM 的成功标准** | 能直接拿去贴进 OKR 文档：一张「我们 vs 他们」对比表 + 一句「做 / 不做」的理由。 |

**隐含的系统能力**

- **功能粒度结构化**：要能把「AI 会议纪要」拆成子能力逐项对比（实时转写 / 摘要 / 待办抽取 / 多语言…）。
- **AppStore / 社媒情感分析**：用户怎么评价是关键证据。
- **「我们 vs 他们」对比表模板**：这是和场景 1 最大的区别——这里要明确的对比矩阵。

> 这是当前 Demo 主场景（AI 编程工具 · 代码补全体验）所属的类别。

## 场景 3：定价 / 商业化决策

> 「下个月要发新模型，定多少钱？三家友商最近半年价格怎么走的，企业版套餐都包含什么？」

| 维度 | 内容 |
|------|------|
| **触发语境** | 商业化 / 发布前定价决策，错一档价格直接影响营收，对数据准确性和时间维度要求最高。 |
| **输入** | 定价对象（自家即将发布的产品）+ 竞品列表。 |
| **想要的输出** | 定价矩阵（按 token / 调用量 / SLA 分层）、历史价格曲线、套餐结构对比、用户价格敏感度信号。 |
| **PM 的成功标准** | 能支撑一个能向 CFO / 老板解释的定价区间，且每个数字可溯源到友商官方价格页。 |

**隐含的系统能力**

- **定价 Schema 高度结构化**：分层维度复杂（token / 席位 / SLA / 企业版增项），不能只存一个「价格」字段。
- **历史快照能力**：「最近半年怎么走的」要求系统对同一竞品定价做时间序列留存——**这条直接逼出「持续监控 / 档案化」功能**，是区别于一次性报告器的关键。
- 信源要求：友商官方定价页 + 历史快照，准确性优先级最高。

## 场景 4：竞品大更新事件响应

> 「Cursor 刚发了 Composer，老板在群里 @ 我，半天内要给个 quick read：要不要跟、怎么跟。」

| 维度 | 内容 |
|------|------|
| **触发语境** | 竞品突发动作，PM 被动且紧急，老板在等。这是**唯一非「主动发起」**的场景。 |
| **输入** | 一个事件链接（推文 / 发布会 / changelog）。 |
| **想要的输出** | 影响评估、跟进必要性、应对方案候选、内部对齐话术。 |
| **PM 的成功标准** | 半天内交一页 brief，能在群里直接转发，老板看完知道「跟 / 不跟、为什么」。**不要长报告。** |

**隐含的系统能力**

- **事件驱动触发**：区别于「按需启动」，系统要能从一条链接起步，而非一个分析配置。
- **快响应模式**：输出 1 页 brief，不是完整报告——**输出模板必须分级**。
- **与历史报告自动 diff**：「这次更新相对上次我们了解的，变了什么」，再次要求档案化。

## 场景 5：季度战略汇报

> 「Q2 review 下周要交，把这个季度三个主要竞品的动作、市场份额变化、关键人事变动汇总一下。」

| 维度 | 内容 |
|------|------|
| **触发语境** | 周期性战略复盘，PM 要把一个季度积累的零散观察汇总成给上层看的总览。 |
| **输入** | 时间窗（Q2）+ 竞品列表。 |
| **想要的输出** | 季度动作时间线、份额变化、组织 / 招聘动向、机会风险清单。 |
| **PM 的成功标准** | 一份能直接进季度 review 的总览，体现「这三个月发生了什么、对我们意味着什么」。 |

**隐含的系统能力**

- **跨时间窗聚合**：不是单次报告，而是把档案里积累的内容按季度聚合——**强依赖档案化**。
- **非传统信源**：招聘 JD / LinkedIn 反映竞品在押注什么方向，是战略信号的重要来源。
- 输出偏「时间线 + 趋势」，又是一种新模板。

## 场景 6：用户流失 / 口碑洞察

> 「用户为啥都跑去用 Kimi？看下小红书、知乎、AppStore 最近三个月的吐槽，主要是哪些场景我们打不过。」

| 维度 | 内容 |
|------|------|
| **触发语境** | 数据上看到流失 / 增长乏力，PM 要定位「我们具体输在哪个场景」，需求强烈且情绪驱动。 |
| **输入** | 流失信号或具体竞品名。 |
| **想要的输出** | 用户负面反馈聚类、场景化弱点定位、迁移成本估算。 |
| **PM 的成功标准** | 能指着具体用户原话说「就是这个场景，用户因为 X 走的」。**溯源价值在所有场景里最高。** |

**隐含的系统能力**

- **UGC 大规模采集**：小红书 / 知乎 / AppStore 评论，采集 Agent 不能只会爬官网。
- **情感 / 主题聚类**：把海量吐槽聚成「场景化弱点」。
- **引用具体用户原话**：每个结论挂真实 UGC 原文，这是本系统「证据链可复现」原则的最强体现。

## 7. 6 个场景反推出的系统能力清单

把 6 个场景横着看，会发现它们对系统提出了四组共性要求——这是设计文档真正要回应的：

### 7.1 触发模式不止「按需」

| 触发模式 | 场景 | 系统含义 |
|----------|------|----------|
| 按需发起 | 1 / 2 / 5 / 6 | 用户主动给配置 → 出报告（当前 Demo 形态） |
| 持续监控 + 历史快照 | 3 | 对竞品定价等做时间序列留存 |
| 事件驱动 | 4 | 从一条链接起步，自动评估影响 |

系统至少要支持这 3 种触发模式，而非只有「按需」。

### 7.2 输出模板不止「长报告」

- 场景 4 → 1 页 brief
- 场景 5 → 时间线
- 场景 6 → 原话引用集
- 场景 2 → 对比矩阵
- 场景 1 → 玩家地图 / 分层

→ **Schema / Writer 要按模板分型**，不能一套长报告模板硬套所有场景。

### 7.3 档案化能力（最大的架构分水岭）

场景 3 / 4 / 5 都要求「对同一竞品持续积累、能 diff、能按时间窗聚合」。这是「竞品情报档案系统」与「一次性报告生成器」的根本区别，也是产品壁垒所在。

### 7.4 信源差异化

- 场景 6 重度依赖 UGC（小红书 / 知乎 / AppStore）
- 场景 5 需要招聘 JD / LinkedIn
- 场景 3 需要历史价格快照

→ 采集 Agent 必须是**多适配器、可按场景选源**的，不能只会爬官网。

## 8. MVP 取舍建议

3 周做 6 个场景必然全部做不深。建议 MVP 砍到 **场景 2 + 场景 4 + 场景 6** 的组合：

| 场景 | 覆盖的触发模式 | 覆盖的能力亮点 |
|------|----------------|----------------|
| 场景 2（Roadmap） | 按需 | 功能结构化对比矩阵（当前 Demo 主力） |
| 场景 4（事件响应） | 事件驱动 | 1 页 brief + 与历史 diff |
| 场景 6（口碑洞察） | 按需（UGC 源） | UGC 采集 + 情感聚类 + 原话溯源 |

这三个组合的好处：覆盖了「按需 / 事件驱动 / UGC 信源」三种典型模式，互不重复，且每个都能演示出完整闭环。其余场景（1 / 3 / 5）作为**扩展叙事**写进答辩，论证系统的泛化与商业化空间，但不实现。

## 9. MVP 三场景 User Journey

下面把 MVP 的三个场景各画一条完整路径：用户从触发到拿到结果的每一步、心里的 OS、系统该做的事，以及这一步对 Agent / Schema 的反推。读法——**「用户动作 → 系统响应 → 反推设计」**。

---

### 9.1 场景 2（Roadmap）User Journey

> 主角：负责会议协作产品的 PM，季度 OKR 评审前 3 天。

| # | 用户动作 / OS | 系统响应 | 反推设计 |
|---|---------------|----------|----------|
| 1 | 「下季度要不要做 AI 会议纪要？得有数据支撑。」打开系统。 | 提供输入页：分析对象（功能名）+ 竞品名单 + 关注维度。 | **Intake**：本场景输入完整，问询层只需补「关注哪几个子能力」。 |
| 2 | 填：功能=AI 会议纪要；竞品=Otter / Fireflies / 飞书妙记；维度=转写准确率 / 摘要 / 待办抽取 / 定价。 | 校验竞品可识别，锁定 `analysis_meta`。 | 复用现有 `products.yaml` 别名机制；维度即 feature_tree 的分支。 |
| 3 | 等待，期间想看到「它真在干活，不是转圈」。 | 进度回调：Collector 采集中 → Analyzer 比对中 → Reviewer 校验中。 | **进度可观测**（已有 P0 修复）；四节点状态外显。 |
| 4 | 报告出来，先看「我们 vs 他们」对比表。 | Writer 渲染功能成熟度矩阵，每格挂 chip `[SXXXXXXX]`。 | **Writer 对比矩阵模板**；feature_existence + performance_quality 两类证据支撑每格。 |
| 5 | 对某格「Otter 待办抽取=成熟」存疑，点 chip。 | 跳转到原始证据：Otter 官网截图 / 用户评价原文。 | **证据链溯源**（核心原则 3）；evidence_id 必须真实可跳。 |
| 6 | 看 SWOT + 优先级建议，决定「做，但只做摘要+待办」。 | Analyzer 输出 recommendations + priority_score。 | **derivations 步**：swot / rec 基于 facts 推导，priority 按权重算。 |
| 7 | 把对比表和建议截图贴进 OKR 文档。 | —— | 输出要可直接复用（表格 / 徽章干净，正文无 quality_score）。 |

**这条 journey 对系统的硬要求**：对比矩阵模板 + 逐格溯源 + 可推导的优先级建议。这正是当前 Demo 已覆盖的形态。

---

### 9.2 场景 4（事件响应）User Journey

> 主角：被老板在群里 @ 的 PM，手上只有一条 Composer 发布推文链接，半天交活。

| # | 用户动作 / OS | 系统响应 | 反推设计 |
|---|---------------|----------|----------|
| 1 | 「老板等着，我没空填一堆配置。」把链接贴进系统。 | 接受**单链接输入**，自动从链接抽取「是谁、发了什么」。 | **事件驱动触发**：起点是 URL 而非分析配置；需要一个「事件解析」前置步骤填充 meta。 |
| 2 | 「这次更新到底是啥、相对之前变了什么？」 | Collector 抓事件正文 + 拉取该竞品的历史档案做 diff。 | **档案化 + diff**：要求竞品有历史快照可比；无档案时降级为「仅本次解读」。 |
| 3 | 「我要的是判断，不是科普。」 | Analyzer 输出影响评估 + 跟进必要性 + 应对方案候选。 | derivations 复用，但**输出粒度更轻**：结论先行，少铺证据。 |
| 4 | 「给我能直接转群里的一页东西。」 | Writer 用 **brief 模板**：1 屏内，结论 / 影响 / 建议三段。 | **输出模板分级**：brief ≠ 长报告；Writer 需按 `report_template` 分流。 |
| 5 | 扫一眼觉得靠谱，转发群里 + 加一句自己的判断。 | 关键结论仍挂 chip，可点开但默认收起。 | 溯源能力保留，但默认不展开，服务「快读」节奏。 |

**这条 journey 引入的新东西**：① 事件解析前置节点（URL→meta）；② brief 短模板；③ 历史 diff（依赖档案化）。这是相对场景 2 需要新建的能力。

---

### 9.3 场景 6（口碑洞察）User Journey

> 主角：看到流失数据的 PM，想知道「用户为啥跑去用 Kimi」。

| # | 用户动作 / OS | 系统响应 | 反推设计 |
|---|---------------|----------|----------|
| 1 | 「具体输在哪个场景？官网没用，要看真实吐槽。」输入竞品=Kimi，信号=用户流失。 | Intake 追问：关注平台（小红书 / 知乎 / AppStore）+ 时间窗。 | **信源可选**：采集 Agent 要能按场景选 UGC 适配器，而非默认官网。 |
| 2 | 选：小红书 + AppStore，近 3 个月。 | Collector 启用 **UGC 适配器**，大规模抓评论。 | **多适配器采集**：UGC 源 ≠ 官网源；需新 SourceAdapter + 三层降级兜底。 |
| 3 | 「别给我一堆零散评论，告诉我规律。」 | Analyzer 对负面反馈做**主题 / 情感聚类**，聚成场景化弱点。 | **聚类能力**：user_pain 不再是单条，而是「聚类簇 + 代表原话」。 |
| 4 | 「这个结论可信吗？」点开某个弱点簇。 | 展开簇内 N 条真实用户原话，每条挂来源链接。 | **原话溯源价值最高**：evidence 必须存 `extracted_snippet` 原文，禁止改写。 |
| 5 | 定位到「长文档处理场景我们打不过」，估算迁移成本。 | Analyzer 输出场景化弱点 + 迁移成本信号。 | derivations 扩展：从 pain 聚类推到「弱点定位 + 迁移成本」。 |
| 6 | 拿原话集 + 弱点结论去开复盘会。 | Writer 用**原话引用集模板**：弱点 → 代表原话 → 影响。 | 又一种输出模板；强调引用密度而非分析篇幅。 |

**这条 journey 引入的新东西**：① UGC 采集适配器；② 情感 / 主题聚类（Analyzer 新能力）；③ 原话引用集模板。溯源原则在这里被推到极致。

---

### 9.4 三条 journey 的反推汇总

| 能力 | 场景 2 | 场景 4 | 场景 6 | 是否 Demo 已有 |
|------|:------:|:------:|:------:|:--------------:|
| Intake 问询层 | ●（轻） | —— | ●（选源/时间窗） | 已有 |
| 事件解析（URL→meta） | —— | ● | —— | 待建 |
| 多适配器采集 | 官网 | 事件+档案 | UGC | 部分（待加 UGC 源） |
| 档案化 + diff | —— | ● | —— | **待建（架构分水岭）** |
| Analyzer 聚类 | —— | —— | ● | 待建 |
| Writer 模板 | 对比矩阵 | brief | 原话引用集 | 仅有长报告/矩阵 |
| 逐条溯源 chip | ● | ●（收起） | ●（原话） | 已有 |

**结论**：场景 2 基本是现状；场景 4 的增量是「事件解析 + brief 模板 + 档案 diff」；场景 6 的增量是「UGC 采集 + 聚类 + 引用集模板」。其中 **档案化** 是被两个场景共同要求、且改动最大的一块，建议作为 MVP 之后的第一优先扩展，或在 MVP 内先做最小版（同竞品报告留存 + 简单 diff）。

---

## 10. 下一步

User journey 已定义「用户怎么走、每步要什么」。建议下一步：把 §9.4 的「待建能力」逐项落到 `design-v2.2.md`——重点是 **事件解析节点**、**Writer 模板分型（report_template 字段）**、**Analyzer 聚类**、**档案化最小版**，并相应扩 `AgentState` 与 Schema 字段。
